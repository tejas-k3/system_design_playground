# System Design Playground

Sketch a system, send traffic, watch it break, then fix it. A browser-based simulator for learning
system design: drag servers, caches, databases, queues and more onto a canvas, wire them together,
press Play, and see queues fill, connection pools run dry, retries pile up and stale reads appear.
Guided challenges start from a broken design and score your fix from one to three stars.

**Try it online:** https://system-design-playground-5yon.onrender.com (a free server that sleeps when idle, so the first load can take up to a minute).

```
frontend/   React + TypeScript + Vite + zustand + roughjs (hand-drawn canvas)
backend/    Go: deterministic discrete-event simulation engine, REST API, WebSocket live sessions
```

The simulation runs on the Go server. The browser edits the diagram, streams it to the server over a
WebSocket and renders the stats and request particles that come back, so edits apply to a running
simulation live.

## Quick start

### 1. Prerequisites

Pick **one** route:

- **Docker** (easiest, nothing else to install): any recent Docker Desktop or Engine, plus `make`.
- **From source**: Go 1.23+ and Node 22.12+ (macOS: `brew install go node`; check with `go version` and `node -v`), plus `make`.

### 2. Get the code

```sh
git clone https://github.com/tejas-k3/system_design_playground.git
cd system_design_playground
```

### 3. Run it

**Docker, in the background** (recommended for trying it out):

```sh
make up               # builds the image and starts it; restarts after a reboot or crash
# open http://localhost:8090
make logs             # follow the server log (Ctrl-C to stop following)
make down             # stop and remove it (shared designs are kept in the sdp-data volume)
```

**From source, one process** (builds the UI and serves it from the Go binary):

```sh
make install          # once: installs the frontend dependencies
make run              # builds both, then serves http://localhost:8090 (Ctrl-C to stop)
```

**For development** (live reload while you edit the frontend):

```sh
make install          # once
make dev              # Go API on :8090 + Vite on :5173; open http://localhost:5173
```

Use `PORT=9000 make up` (or `run` / `dev`) to change the port. Other targets: `make test`, `make lint`
(gofmt + staticcheck), `make bench`, `make build`, `make docker-run` (Docker in the foreground); `make help` lists all.
For configuration, reverse proxy, metrics and capacity notes see [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

### 4. First steps in the app

1. On the welcome screen choose **Load an example**, then press **Play** (or Space) and watch traffic flow.
2. Or open **Challenges** and start with *Hello, database*: each challenge starts broken and tells you its goals.
3. Everything you build is saved in your browser; **Share** (toolbar) copies a link to the current design.

### Troubleshooting

| Symptom | Fix |
|---|---|
| Page says "Can't reach the simulator" | The Go server is not running. Use `make up`, `make run`, or `make dev` (which starts both). |
| `address already in use` / port 8090 taken | Pick another: `PORT=9000 make up`. |
| `go: command not found` or an old Go | Install Go 1.23+ (`brew install go`) or use the Docker route. |
| `npm install` warns about the Node version | Install Node 22.12+ or use the Docker route. |
| Status dot is red / "Disconnected after being idle" | Idle sessions close after 10 minutes; press Play and it reconnects. |
| `make up` / `docker build` sits for minutes at "load metadata" or "pulling" | Docker Hub or gcr.io is unreachable or throttling you. Check `curl -sI https://registry-1.docker.io/v2/` first. The Dockerfile pins every base image by digest, so once the images are cached a rebuild needs no network for them; if the pull keeps stalling, build without Docker (`make run`) or retry later. To refresh the pins deliberately: `bash docs/review/tools/image-digests.sh`. |
| Want a clean slate | Clear the site's local storage in your browser; for Docker designs also `docker volume rm sdp-data` after `make down`. |

See [docs/COMPONENTS.md](docs/COMPONENTS.md) for what each component does, exactly when it fails, and why those rules are believable.

## How to play

1. **Build.** Click or drag components onto the canvas. Drag from the round handle on a component's
   right edge to connect it to another component (invalid connections are refused with a message).
2. **Run.** Press **Play** (or Space). Bars show how busy each component is; the metrics drawer shows
   throughput, latency, success rate and a breakdown of *why* requests failed.
3. **Break it.** Select a component and press **Crash it**, or raise the traffic.
4. **Fix it.** Change settings or structure while it runs.
5. **Follow a request.** Open the **Request traces** tab under the canvas, pick a failed or successful request
   and read its waterfall: hatched bars are time spent waiting in a queue, red marks where it failed, and
   faded bars are work that kept running after the user gave up. A one-line diagnosis says where the time
   or the failure came from.

Open **Challenges** for guided scenarios. Each has goals (success rate, latency, cost, double
bookings, stale reads…), three hints, a prediction question, a reference solution you can reveal after
the hints, and a debrief. Some are *configuration only*: the architecture is fixed.

Shortcuts: `Space` play/pause · `V` select · `C` connect · `Delete` remove · arrow keys move (Shift: far) · `Ctrl/⌘ Z` undo ·
`Shift+Z` redo · `F` fit view · `+`/`-` zoom · double-click empty space for a note · `Esc` cancel.

**Without a mouse or on a phone:** the first Tab stop on the canvas is a list of every component (Enter selects one);
the inspector's "Sends requests to" section connects and disconnects components from a dropdown, so nothing
requires dragging. On a touch screen, pinch to zoom and drag to pan; below 980 px wide the panels start closed
and the inspector becomes a bottom sheet.

## What is simulated

| Area | Behaviour |
|---|---|
| Traffic | Independent (Poisson), bursty (short rushes, same average) or closed-loop users (a fixed crowd that waits and thinks); Poisson arrivals; constant / ramp / spike / wave or authored curves; read/write mix; Zipf, uniform or scan key popularity; hot key |
| Clients | Timeouts, retries with exponential backoff + jitter or immediate retry; abandoned ("ghost") attempts keep consuming resources downstream; optional DNS record TTL keeps a failed target in rotation until expiry, counts lookups and charges $0.00001 per lookup |
| Service times | Steady by default; an advanced *service-time spread* setting (app server, database, worker, external API) switches to exponential or heavy-tailed, same mean, to show how variability lengthens queues and tails |
| Autoscaling | Optional per app server: a fleet of identical servers that grows when the last 30 s of thread utilisation is above a target, after a boot delay, and shrinks one server at a time after a quiet period; cost is the average number of servers that ran |
| App servers | Thread pool, bounded FIFO/LIFO queue, queue-wait timeout, call timeouts, circuit breaker, idempotency keys |
| Connection pools | Per server per database; databases refuse connections beyond their limit |
| Caches / CDN | LRU, LFU, FIFO, random eviction; TTL (with optional jitter); warm start; optional sharing of concurrent misses; read-through or cache-aside; what a write does to cached copies: nothing (pull: stale until the TTL), invalidate or write-through (push: every cache is told of every write) or a lease (only the caches that hold the item are told). The messages sent to caches are counted and can be a goal. Measured with four caches that each hold 15% of the items and a third of the traffic writing: pull sent 0 messages and served 1.8% stale reads, push sent 9,332 and none stale, a lease sent 1,457 and none stale. A share of items can have a shorter TTL, and a cache can revalidate an expired but unchanged entry for about a tenth of a full read (the check is modelled as a cost on the cache, not as traffic to the origin; in a test the database saw fewer arrivals) |
| Replication | Replica serves the version from `now − lag`; strong / bounded / eventual reads and a stale-read count; optional failover: promote a replica after a detection and promotion time, losing writes newer than its lag (or nothing, with a synchronous replica that slows every write); an unfenced old primary that returns loses the writes made since |
| Load balancing | Round robin, least connections, random; health-check delay; outlier ejection |
| Queues | Bounded queue + workers, retries, backlog and job-latency metrics |
| Rate limiter | Token bucket |
| Sharding / geo / leaderboard / booking | Shard routing by key; spatial index; Redis sorted-set style ops; row locks and Redis locks with TTL, double-booking detection |
| Chaos | Crash (auto-restart), slow-down (steady or pulsing) and network-partition events, scheduled or manual |
| Question formats | Beyond fixing a broken design: **warm-up** (twelve needs, pick the component for each; graded together, with the reason shown afterwards), **assumptions** (match eight distributed-systems failure cases to the assumption they break), **requirements** (a one-line brief and eight candidate clarifying questions: ask up to three; the ones that change the design are those whose answer flips a reference design from pass to fail, checked by running it both ways), **estimate** (numbers graded within 30% / 2x, then built into a fleet and tested against the real peak), **diagnose** (a dashboard and one failed trace generated from a seeded run, pick the cause), **trade-off** (run each candidate design, then choose against a stated requirement), **review** (tick the flawed components; scored by found, missed and false marks) and **open** challenges (blank canvas, hidden load and failures, no solution to reveal; the first one, a link shortener, adds a starter checklist that ticks as you place and connect components). Five SDE2 open briefs cover a shortener, notifications, a news feed, nearby search and chat; after a pass, each shows a local checklist of remaining weak points. New fix challenges cover secondary indexes for typeahead and exact or Bloom-filter URL deduplication in a crawl frontier. Every answer key stays on the server until you submit |
| Interview mode | A timed mock interview in seven stages (requirements, estimation, API, data model, high-level design, deep dive, trade-offs): a countdown computed from timestamps, so a hidden tab cannot drift it; a calculator (users to QPS, peak, storage, bandwidth, servers) with a warning when a payload is too big for a message queue and a *Build a starter* button; requirements, API and data-model pads with interviewer-style prompts; a test of your design against your own availability and latency targets; a self-rating beside evidence from the lint and the last run; PNG and Markdown export; and a present mode driven by the arrow keys. Everything is kept in this browser (localStorage), nothing is sent to the server. The API pad asks how a list is paged, whether a POST needs an idempotency key and what a failure returns; the data pad flags a lookup by a field that neither the key nor an index covers |
| Daily challenge | The welcome screen offers one challenge a day: every challenge takes a turn before any repeats, never the same one two days running, chosen from the date alone. A streak counts consecutive days it was solved, kept in this browser only (localStorage), with no accounts and no leaderboard |
| Skill map | Every challenge is tagged with the ideas it practises (ten concepts: capacity, caching, replication, consistency, queues, failure handling, sharding, overload control, storage and payloads, autoscaling). The skill map lists one row per concept with the stars earned out of those available and a button for the challenge to try next (fewest stars first, easiest first), computed from the stars kept in this browser |
| Glossary | Forty-five terms (percentiles, utilisation, Little's law, secondary index, crawl frontier, circuit breaker, retry storm, idempotency, stampede, replication lag, split brain, fencing, sharding, hot key, backpressure, load shedding, SLO, the eight common distributed-systems assumptions, distribution transparency, dependability and more) with a one-sentence and a fuller definition. In challenge stories, hints and debriefs a marked word is keyboard-focusable and shows its definition on hover or focus (read out by screen readers, closed with Escape), with a button to a challenge about it |
| Alternatives compared | After a challenge is solved, a table shows what would have happened had you only done something else on the broken design (for example, letting clients retry, or adding threads), with the measured pass or fail, success rate, p95 and cost. A **Defend your design** step also runs one stored counter-question on the learner's own design and compares the two results. Every stored row is re-run by a test against the engine, so the numbers cannot drift from the simulator |
| Feed fan-out | A **feed** workload with Zipf-skewed followers and an app-server strategy: push on write (a post costs one insert per follower, so celebrities flood the database), pull on read, or a hybrid that pulls the few huge accounts; the overview counts timeline inserts and followed authors read |
| Overload control | Users with distinct accounts and a rate limiter that limits per user or for everyone, with token bucket, fixed window and sliding window algorithms; bot traffic (a scraper that defeats caches and never retries); a client retry budget (stops retry storms); per-dependency bulkheads; deadline propagation (skip work whose client has gone); priority shedding when the queue is long. The customers-only score sets bots aside. A **leaky bucket** limiter smooths a burst instead of turning it away: with a burst of five times the rate, the busiest second at the app server was 426 requests a second through a token bucket and 100 through a leaky bucket (the cost is the wait). Accounts can be grouped into **tenants** and the limiter set to count per tenant: with one tenant sending 400 requests a second and three sending 50, one shared limit left the quiet tenants with nothing and a limit per tenant left them all of theirs. The challenge "The noisy tenant" scores the worst-served quiet tenant |
| Hot keys | One item taking most of the reads (hot item share) can pile onto a single cache node; an app server can keep its hottest items in a small local cache (size and lifetime set), which shows as local cache hits and takes that load off the cache node. A write through that server drops its own copy; other servers keep theirs until they expire . A shard router can spread by key (one hot map cell lands on one shard) or by request (even load; reads of one key would then need every shard, not modelled). A database can also put a lock on every row it writes (*Row locks on every write*): writes to one popular row then run one after another and keep their connections while they wait, so the row caps what it can take at 1 / write time (47.9 writes a second against 50 predicted with 20 ms writes) and most of what it commits is for clients that already gave up (4.3 a second reached a waiting client); an app server can split the hot item over several rows (a counter split over 8 rows brought 200 writes a second, 90% of them on the item, back from 2% to 99.6% success), at the cost of reads that add the rows up The challenge "Launch day" puts 90% of 200 writes a second on one locked row (20 ms each, so 50 a second): nothing succeeds, 256 database connections do not help ($7.83/hr), 2 sub-rows are not enough, and splitting the counter over 8 rows gives 100% success at p95 185 ms (2 stars on four seeds); 4 rows pass on three seeds with a p95 of 432 to 468 ms, but miss the 500 ms goal on seed 42. The run summary shows the busiest item's share of all requests once it reaches 5% (0.398 with 40% of requests aimed at one of 5,000 items, theory 0.40). |
| Resharding | A shard router places keys either by hash mod n or on a consistent-hashing ring with several points (virtual nodes) per shard. When a shard is added or removed while running, the router reports the share of keys that moved: about 4 in 5 with mod, about 1 in 5 with the ring (measured on 4 to 5 shards), and more points per shard even the load out. With a time to move the data set, a request for a key that is still moving pays extra for that long: in a test, adding a fifth shard slowed 1,112 requests with mod and 333 with a ring (about 4 in 5 against 1 in 5 of the requests in a 15 s window). A scheduled "add a node" chaos event gives a router a fifth shard under load, and the challenge "Adding a shard under load" shows hash mod n taking p95 to about 2.5 s while a ring stays at 154 ms |
| Hedged reads | An app server with several identical read replicas can take turns between them and hedge: a read not answered after a set time is asked of another replica too, and the first good answer wins. With replicas whose reads have a heavy tail (one read in twenty is far slower), hedging after 60 ms cut the p99 from 285 ms to 192 ms with 8.4% of reads hedged; more threads did not move the tail. The challenge "The slow one in a hundred" uses it |
| Regions | Every component, users included, can be placed in a region (US, Europe, Asia-Pacific; the default is US). A call between regions pays the distance each way (US-Europe 45 ms, US-Asia 75 ms, Europe-Asia 100 ms): users in Europe on US servers measured +91 ms at the median (theory 90) and in Asia +152 ms (theory 150), and a database in another region taxes every call by about +90 ms. A region outage takes down everything in a region together. Zone-aware load balancing and replicas per zone are not modelled yet. A user group can be sent to the nearest region (*Send users to the nearest region*), and to the next nearest when that one is down: with the eu stack down for 15 s, success was 75.7% taking turns and 99.1% with geo routing, and the median for users in eu fell from 181 ms to 127 ms. The challenge "Go global" has users on three continents and one US stack (p95 291 ms; a stack per region with geo routing gets 151 ms) |
| Zone-aware balancing | A load balancer can prefer the servers in its own availability zone ("Own zone first"), which saves the hop between zones (mean latency 133.4 ms to 130.0 ms with half the servers in another zone). "Fail over to other zones" decides what happens when none is left in its zone: on, the other zone takes over (97.0% of requests succeed through a 20 s loss of the local server); off, they have nowhere to go (49.5%). Off by default (any zone). A "configPush" chaos event gives one setting a new value on every component of a kind (or on one component) at once, as a configuration rollout does, and puts the old value back after a while: a bad value on both app servers (40 ms per request instead of 20) takes success from 98.2% to 91.0% over a 40 s run, and only for the 10 s the value lasts. Read replicas now run further behind the farther they are from the primary: the replica's own copy lag plus the round trip to the database (nothing in the same zone, 3 ms across zones, 90 ms between the US and Europe, 200 ms between Europe and Asia-Pacific): 100 ms of copy lag becomes 100, 103, 190 and 300 ms; a synchronous replica has none. A failover to a replica in another region therefore loses more of the recent writes. A component placed in a region or zone shows it on its tile in words with a small pin ("eu · az-b"), so where it runs is never only a colour. |
| LLM server | An LLM Server has GPUs that each run a batch of answers: a new request is admitted when there is a place in the batch and its prompt-plus-answer tokens fit in the GPU's KV cache, its prompt is read first (prompt tokens / reading speed, during which the GPU's other answers wait), then every decode step gives one token to every answer in the batch and takes a base time plus a little per answer. Stats: time to first token and the gap between tokens (p95), tokens per second, average batch, GPU busy share. The model is checked by hand: a lone request's first token comes after 45.2 ms (hand calculation 45.5) with a 20.5 ms gap between tokens; throughput at batch sizes 1, 4, 16 and 64 is 43, 125, 233 and 306 tokens a second against the model's 43, 125, 235 and 302 (near-linear, then flattening); a 3,000-token KV cache with 1,100 tokens per answer holds exactly two; four GPUs give 733 tokens a second against one GPU's 183; an overloaded server's p95 first token is 8.1 s against 151 ms when idle. Goals can limit the p95 time to first token. Token-aware rate limiting and a vector store are not built yet. The challenge "Slow first token" (one GPU writing 4 answers at once under 3 requests a second): the first token waits 57 s on every seed; writing 64 answers at once brings the p95 first token to 432 to 682 ms on nine seeds within a budget that does not allow a second GPU, while 16 at once still waits 8 to 19 s and a second GPU at a batch of 4 is both too slow and over budget. A rate limiter can count tokens instead of requests ("Count: Tokens (weighted)" with an allowance in tokens a minute and a one-minute burst); users can carry a token count per request and a share of huge requests (20 times as many). Measured: an allowance of 54,000 tokens a minute against 10,000 tokens a second admits 9.9% of requests over 600 s (theory: burst plus 900 a second = 9.9%); with 5% huge requests against an allowance of 12,500 tokens a second, 393 of 12,019 requests are refused and nearly all of them are the huge ones. A Vector Store searches embeddings approximately: a search takes a fixed time plus a time per candidate examined, and recall (the share of the true nearest neighbours found) is 1 - 0.5^(candidates / 32), so more candidates find more and take longer (checked by hand at 16 to 512 candidates: 4.8 to 29.6 ms, recall 0.29 to 1.00, request time strictly rising); the index needs vectors x dimensions x 4 bytes times 1.5 of memory (92.2 GB for 10 million vectors of 1,536 dimensions, as calculated) and its price follows its memory. An app server connected to both a vector store and an LLM server retrieves first, then generates: the answer takes the search time (plus a hop) longer, and the model's own first token is unchanged (45.2 ms either way). A goal can require a vector search recall. The challenge "Search under load" (150 searches a second on four search cores, 20 million vectors): the default of 512 candidates (recall 100%) answers 19 to 34% in time with a p95 near 2.9 s; 160 candidates (97% recall) answers everything at a p95 of 143 to 146 ms; 64 candidates is fast but finds only 75%, 32 cores keep full recall but cost $2.80 an hour against a $2 budget, and 8 cores pass. The challenge "The GPU budget" (one GPU, 2 requests a second, one in ten carrying a 10,000-token prompt) fails on every seed with a p95 first token of 6.1 to 10.5 s; a token limiter with an allowance of 56,000 tokens a minute brings it to 0.3 to 1.2 s on nine seeds while still serving at least 80% of requests (the refusals are nearly all the huge prompts), a second GPU is over budget, and 45,000 tokens a minute turns away too many. A request's prompt length now sets the model's prefill when the users give one. |
| Stream job | A stream job can recover from a crash with a message log instead of a checkpoint alone: it replays the logged events and repeats no output, catching up in 1.24 s against 2.21 s with a 20 s checkpoint ("Restart the counter"), for a log write per event. A Stream Job counts events in windows of event time (tumbling, or sliding with a slide), emits a window when the watermark (newest event time minus a delay) passes its end, updates it for late events within the allowed lateness and drops them beyond it. At-least-once delivery repeats the windows that fired since the last checkpoint after a crash; exactly-once does not, at a little extra time per event. Measured: with 10% of events 8 s late, a 2 s watermark delay and 10 s windows, 373 of 6,000 events are dropped (theory 360) and 10 s of allowed lateness turns them into 373 window updates. Bloom filter, count-min, HyperLogLog and top-K exist as tested code (error within theory) but are not yet components. The challenge "Count the clicks" drops 1,788 late clicks on seed 42 (1,800 to 1,814 on four seeds); allowing 30 s of lateness drops none and still publishes each window within 2 s, while waiting 25 s for stragglers also drops none but fails the 3 s freshness goal, and 15 s of lateness still drops 550. Goals can limit dropped late events and the wait for a window's first result. A stream job can also count different visitors, exactly (a table of ids, 71 KB for 4,577 visitors) or with HyperLogLog (1 KB at 10 bits, 4 KB at 12 bits; 4,672 estimated against 4,577 true at 10 bits, a 2.1% error against the theoretical 3.3%). The challenge "Unique visitors" has a 16 KB budget and a 6% error limit: the exact table fails on every seed, 12 bits passes with under 1% error, 16 bits is accurate but needs 64 KB. It can also find the ten most popular items, exactly (83 KB for a 200,000-item Zipf catalogue in a 60 s run) or with a count-min sketch and candidate list (1,000 x 3 counters = 12.2 KB finds 9 or 10 of the true ten on nine seeds; 40 x 2 finds 2 or 3). The challenge "The top ten" has a 16 KB budget and needs 8 of 10: the exact table fails on every seed, the 1,000 x 3 sketch passes on all, a 4,000 x 4 sketch finds all ten but needs 63 KB. The Bloom filter is also a component of an app server: with users who ask for ids that do not exist ("Asks for what is not there") and "Bloom filter in front of reads" on, absent ids are answered at once and only the filter's false positives reach the database. At 5 bits per id and 3 hashes the measured false-positive rate is 8.9% against the formula's 9.2%, and the database's reads fall from 59,870 to 32,547 over two minutes when half the requests are for absent ids (expected 32,684). |
| Polite crawler | An external service can refuse callers that exceed what it tolerates ("Calls it accepts": past that many a second it answers 429), and an app server can pick one of several external services by the request's key (as a crawler picks a site) and limit its own calls per second to each ("Calls per second to one service"; excess calls wait their turn). Measured on a crawler whose traffic comes in rushes of 16 calls a second against sites that tolerate 8 (average 4): without a limit 252 to 410 fetches are refused on nine seeds and 71 to 79% succeed; limiting to 8 a second per site refuses none and succeeds on every seed, at a p95 of 2.8 to 5.5 s (the price of smoothing the rushes). A URL frontier with deduplication and crawler traps is not modelled. Users can now run a crawl workload ("Workload: crawl"): each request fetches a URL from a frontier of pages on Zipf-skewed sites; pages link to new and already-known pages; a trap site generates endless new links unless "maxDepth" caps it (frontier 12,232 and growing after 120 s without a cap, 50 with a depth of 6); the seen-URL check is none, an exact set (16 bytes per URL) or a Bloom filter whose false positives make the crawler skip new pages (miss rate 1.86% measured against 1.76% predicted, memory 73 KB against 1,561 KB for the exact set). No challenge uses the crawl workload yet. |
| Writes through a cache | An app server wired only to a cache that fronts a database (app, cache, database) sends reads through the cache as before and now sends writes through it too: the cache passes the write on to the database and keeps its own copy current (write-through). Before, every write in that shape failed with "No route" (1,568 of 1,568 at 100% writes); now none fail, and a mix of reads and writes serves 1,460 of 1,460. |
| Levels, hints and progress | Every challenge is written for an interview band (SDE1: fundamentals, SDE2: a whole service and its weak points, SDE3: judgement and failure analysis; 10, 45 and 26 challenges). Pick your level (or All levels) in the challenge picker, on the Welcome screen or in the skill map: it only changes the order, the daily challenge and the skill map's suggestion and never hides a challenge. Prediction options are shown in a fixed shuffled order and are written to be about the same length, so the right one cannot be picked by position or size (a test fails if the right option is the longest in more than 40% of questions, or the longest option is more than 1.6 times the shortest; before, it was the longest in 65 of 74). Hint 3 asks a question instead of naming the fix; the plain answer is one click further on ("Show the answer", `GET /api/scenarios/{id}/answer-hint`). Every Hard challenge has an optional "Go deeper" debrief for experienced engineers (trade-offs, behaviour at scale, a likely follow-up). The browser also remembers how each challenge went (wrong predictions, hints used, attempts before the first pass, whether the answer was shown); the skill map marks a concept "needs review" when a passed challenge needed the answer or had a wrong prediction, and Export/Import progress saves or merges that as a JSON file. Nothing leaves your browser. |
| Glossary everywhere | 40 of the 45 glossary terms are marked in challenge text (stories, hints, answers, debriefs, deeper explanations, predictions and alternatives): a marked word is focusable and shows its definition. A term is only marked where it fits (a tooltip that explains the wrong idea is worse than none, so 23 challenges currently have none in their story or debrief; the test allows at most 24); a test fails below 30 distinct terms in use and when any text strips to something different from its wording. In a prediction option (a button) the plain words show, because a focusable word inside a button is invalid. |
| Daily challenge, offline and by level | A run started from today's challenge card uses a seed taken from the date (one of the eight the challenges are calibrated for, never the same on two days in a row) and says "Today's run: seed N". The last good challenge list is kept in the browser, so the card still shows when the list cannot be fetched ("Showing the last known list"); opening a challenge still needs the server. The skill map also shows stars earned per level (SDE1, SDE2, SDE3) as text and a bar. |
| Collapse a box, name a design | A box (region, zone, VPC, service) can be collapsed to a header chip with a chevron button (keyboard: Tab to it, Space or Enter), by double-clicking its header, or from its inspector panel. Collapse is only visual: the simulation and the saved diagram are unchanged apart from the flag. The chip says how many components it holds and, while running, the busiest utilisation and how many are down or failing (in words and a dashed halo, not colour alone), connections to hidden parts are drawn to the chip and folded per neighbour, search and the keyboard outline still reach hidden members (choosing one opens its box), and undo covers it. The design has a name you can edit at the bottom left (Enter saves, Escape cancels, up to 60 characters): it shows in the browser tab, in the PNG and Markdown exports and in shared designs. |
| More payload and storage | A cache or CDN can keep big objects in pieces (`rangeKB`): a request needs every piece and only the missing ones travel to the origin (a 1 MB object with half its pieces cached costs 0.502 MB of origin traffic per request, 0.5 by hand; 10 users on a cold object fetch exactly 1.00 MB with collapsing, 9.00 without). An object store can take an upload in parts several at a time (`multipartKB`, `multipartParallel`; saves 139.8 and 179.0 ms of a 230 ms upload, 140 and 180 by hand; the link stays the floor). Users can send fixed or lognormal sizes around the same mean (`sizeDist`, `sizeSigma`: same load, heavier tail, p99 291 to 315 ms at 88% link load). Any component can have a network card limit (`nicMbps`, shared by everything it sends: 99.2 a second against 100 by hand). The object store's PUT/GET mix follows the users' read share (0.691 against 0.7). | Quorum key-value store | A Key-Value Store keeps N copies of each key on a cluster of nodes. A write is acknowledged when W copies have it and a read answers with the newest version among the first R replies, so latency is the kth fastest of N. Reads return old data exactly when R + W is not more than N (measured: with N=3, about 11% of reads stale at R=1 W=1, 5% at R=1 W=2, none at R=2 W=2), and losing too many nodes for a key fails it as no quorum. ## Architecture

```
backend/
  cmd/server/            HTTP server entry point (flags / env: ADDR, STATIC_DIR, ALLOWED_ORIGINS)
  internal/engine/       the simulator (no I/O, fully unit tested)
    sim.go                   core types, event loop, 100 ms tick
    topology.go clients.go   building and live-editing the graph; traffic, retries
    flow.go data.go          request flow, pools, queues; per-node behaviour
    chaos.go versions.go     failure injection; item versions and staleness
    trace.go                 sampled per-request traces (observation only)
    registry.go sanitize.go  node kinds and parameters; validation of untrusted diagrams
    scoring.go stats.go      goals and stars; the snapshots the UI renders
  internal/scenarios/    challenges as data (+ tests: start must fail, solution must pass)
  internal/api/          REST + WebSocket session
frontend/src/
  api/ model/ state/     wire types, diagram helpers + sanitizer, zustand store, persistence
  sim/                   WebSocket client and the store ⇄ server bridge
  draw/                  canvas renderer (roughjs), geometry and hit-testing, icons
  ui/                    Board, Toolbar, Library, Inspector, Charts, challenge panel, dialogs
```

The engine is a priority-queue discrete-event simulation. Each request is a chain of callbacks across
nodes; capacity-limited nodes (app threads, DB connections, Redis, workers) are *stations* with a
bounded queue. A 100 ms tick snapshots per-node counters into ring buffers that become the live stats.
A 30 s run of a 1,000 rps, 20-node design takes about 90 ms (`make bench`).

### WebSocket protocol (`/api/sim`)

Client → server: `init {diagram, scenarioId?, seed?, speed?}`, `diagram {diagram}` (live edit),
`play`, `pause`, `step`, `reset`, `speed {speed}`, `traces`, `crash {nodeId}`, `restart {nodeId}`.
Server → client: `frame {status, speed, stats?, particles?, notices?}` (~25 Hz, stats ~10 Hz),
`traces {failed, ok}` (answer to `traces`: the most recent traced requests, newest first),
`result {scenarioId, score}` when a challenge finishes, `error {message}`.

Limits: at most 64 live simulations at once (`-max-sessions` / `MAX_SESSIONS`; further connections get
`503` with `Retry-After`), and a stopped or paused session is closed after 10 minutes of silence
(`-idle-timeout`). The client then goes dormant and reconnects the next time you press Play.

The server advances at most 100 ms of wall time per tick (scaled by speed, in ≤10 ms slices under a
12 ms CPU budget) and warns when it has to slow down. Configuration-only challenges reject topology
changes on the server as well as in the UI.

## Authoring a challenge

Challenges live in `backend/internal/scenarios/defs.go`: a starting `Diagram`, a reference `Solution`,
`Goals`, optional `Traffic` curves and `Chaos` events, three hints, a prediction and a debrief.
`go test ./internal/scenarios` fails unless the starting design fails the goals and the solution passes
them across several seeds, so a mistuned scenario is caught immediately. `VERBOSE=1 go test -v
./internal/scenarios` prints every check.

## Persistence and sharing

The sandbox diagram, theme, view position and challenge stars are stored in the browser's
`localStorage` (`sdp:v1`), validated on load.

The **Share** button saves the current design on the server and copies a link such as `/#design=3ibupvsc57zfg`;
opening it loads the design into your sandbox as an undoable step. There are no accounts: the 13-character
random id is the only access control, so anyone with the link can open that design and nothing else is
readable. Designs live in memory unless the server is started with `-data-dir` (`DATA_DIR`), in which case they
are also written there and survive restarts. At most 5,000 are kept (`-max-designs`), oldest dropped first,
and one client may share 20 a minute.

## Tests

`make test` runs `go vet` + Go tests (engine mechanisms, scenario calibration, API and WebSocket
sessions) and the frontend type-check + unit tests.
