# Components and how they fail

What each component in the simulator does, what makes it fail, and why you can trust (or question) those rules. Every statement here was checked against the engine source (`backend/internal/engine/`) and the tests named in each section. If the code and this file disagree, the code is right and this file is a bug.

## The idea in one paragraph

A request is a chain of calls. Every component it touches holds a **resource** for a while (a thread, a database slot, a token), and when the resource is busy, the request **waits in a queue**. When the queue is full, or the wait is longer than the caller will tolerate, the request **fails** with a named reason. Almost nothing "breaks" at a fixed number: a server does not fail at 400 requests a second, it fails because at that rate its threads stay busy, its queue fills, answers arrive after the user has given up, and those become the failures you see. Only a few limits are explicit settings (queue sizes, connection caps, the rate limiter's rate, thread counts). Everything else is emergent from them.

The simulation is a deterministic discrete-event engine: the same design and the same seed always give the same result.

## Components

Defaults are the values a component starts with; every number is a setting you can change in the inspector.

| Component | Concurrency (what it can work on at once) | Queue before it refuses | What happens when it fails |
|---|---|---|---|
| **Users** | not a server: arrival rate (default 50 req/s; open, bursty or a closed-loop crowd) | none | The user gives up after `timeoutMs` (2,000 ms): the request fails as **Timeouts**. Retries (default 0) add load exactly when the system is struggling; the abandoned attempt keeps consuming resources downstream. With `dnsTtlSec` enabled, a down target stays in rotation for its TTL and stale-address attempts fail as **Stale DNS record**. Request and response sizes (`reqKB`, `respKB`) are fixed by default; `sizeDist: lognormal` with `sizeSigma` (0.5) spreads them around the same mean (a pure function of the seed and the request number, so no random draw is made and a request keeps its size at every hop; sample mean 1.0001 over 100,000 requests at sigma 0.5). The load is the same but the tail is worse: at 88% link load the extra mean wait was 7.5 ms against 8.3 ms from Pollaczek-Khinchine, p99 291 to 315 ms. |
| **Load Balancer** | effectively unlimited by default; with *Most requests a second* (`maxRps`) it passes only that many, and four times as many at layer 4 | none | It fails a request with **No healthy backend** when every backend is down or ejected. A crashed server keeps receiving traffic until the health check notices (default 2 s), and those requests fail as **Node down**. Round robin, least connections or random; optional outlier ejection. *Keep a user on one server* (`sticky`) sends requests from the same user (the Users component needs *Distinct users*) to the server they went to before while it is healthy: it keeps local sessions found, loads servers unevenly when some users are busy, and a server that dies takes its sessions with it. *Works at* (`layer`): layer 7 reads each request (so canary shares and sticky users work) and adds 0.2 ms; layer 4 forwards connections (0.05 ms, about four times the throughput, half the base cost) and ignores canary shares and sticky users. A balancer past its limit queues requests up to *Longest wait* (`lbQueueMs`) and then refuses them (503); its busy level shows, so the bottleneck check names it. Its bandwidth is limited by the network card setting that every component has. |
| **App Server** | `threads` (8) x servers running; each request holds a thread for its whole life, including time spent waiting on a dependency | `queueCap` (50), first-in-first-out or newest-first; optional maximum wait | Threads busy and queue full: **Queue full (503)**. Waited longer than the maximum queue wait: **Waited too long in queue**. A dependency call with no call timeout (default: wait forever) keeps its thread, so a silent dependency fills all threads. With a call timeout: **Call timeouts (504)**. A tripped circuit breaker: **Circuit open**. A crash fails every request in flight on it (**Node down**). Optional stop-the-world GC pauses (`gcPauseMs`, mean every `gcEverySec`, random gaps): for the pause nothing starts or finishes, so latency grows in a tail while the median barely moves. Optional autoscaling adds whole servers after a boot delay. An app server connected to a database and a queue (or topic or log) can tell others about each write (*Tell others about a write*): as a **dual write** it saves, then publishes, and an unreachable queue loses the event for good; with an **outbox** the event is saved with the data and a relay publishes it until it is taken. *Writes that span services* can also be three-phase commit: a pre-commit round is added, so when the server dies the services wait `termTimeoutMs` and then decide alone instead of staying locked (no transaction in doubt, but a third round on every write; the wrong decision a slow or cut-off server can cause is not simulated). The lock-seconds held can be a goal. *Where login sessions live* (`sessionState`): none (stateless), in the server's memory (lost when it crashes) or in a connected Redis (found from any server, one call per request, lost if the store loses its data). A request whose user has signed in before but whose session cannot be found is refused as *Signed out* and the user signs in again (`loginMs`); *Session lifetime when idle* is soft state that expires. Local sessions belong to the component, so the instances of one autoscaled app server share them and never sign a user out between themselves. The run reports sessions lost and requests refused, and a goal can limit them. *Runs as* a container (`runtime`, `containerBootSec`) boots in seconds instead of the VM boot time and costs a fifth less. *Cold start* (`coldStartMs`, `idleSec`, `keepWarm`) models a function that scales to zero: the first request after an idle spell, and those arriving while it boots, wait for the start; keeping one warm costs $0.05 an hour more. *Rank the feed* (`ranking`, `rankCandidates`, `rankUsPerCandidate`) adds model time to every read in proportion to the number of candidates scored (a write is not ranked), so too many candidates saturate the threads; it is a cost model, with no quality of ranking and no per-candidate records. With a saga, *Tries again when an undo fails* (`compensationRetries`) calls a failed undo again after 50 ms up to that many times before the order is counted as stuck; the undo is assumed safe to repeat. |
| **Cache** | 10,000 at once | 2,000 | It rarely fails. A **down** cache is bypassed: every lookup becomes a miss and goes to the data store, so the store takes the whole load. A small or cold cache has a low hit rate; entries that all expire together cause a stampede (see the cache-stampede challenge). *On writes* is pull, push or a lease: *Do nothing* leaves a copy until its TTL ends; *Invalidate* and *Write through* tell every connected cache about every write, one after another, so the write waits for each; *Lease* tells only the caches that hold an unexpired copy of the item (the entry is the lease). The messages sent are counted (*Messages to caches*) and can be a goal. The origin's list of who holds what is charged as extra memory on the cache (about 1.5× the memory part of its cost). *Per-item TTL* gives a share of the items (`shortTtlPct`) a shorter life (`shortTtlSec`) while the rest keep the normal TTL. *Revalidate* (`revalidate`) turns an expired entry whose item has not changed into a cheap check (`revalidateMs`, about a tenth of a full read) that renews it instead of fetching the value again; the renewals are counted (*Revalidated*). The check is a cost on the cache only: the origin is not sent a request, it must be a read-through origin that is up, and it is not used with *Range size*. *Per-item TTL* needs a TTL above 0 and never lengthens an item's life. A CDN is refreshed only by its TTL or a purge; the write policy decides what a cache invalidates, not a CDN. |
| **Database** | `connections` (16 concurrent queries) | `queueCap` (100) | Slots busy and queue full: **Queue full (503)**. More open connections than `maxConnections` (500) across all servers: **DB connections refused**. Crashed: **Node down**, or **No primary: failing over** while a replica is being promoted. Isolation (for the users' Transfers workload): read committed lets two transfers overwrite each other (counted as overwritten updates), repeatable read aborts the second committer (**Transaction aborted**), serializable locks both accounts so transfers wait for each other and deadlocks abort a victim; throughput falls as isolation rises under contention. Data model preset (default relational): document makes single-key reads and writes about 20% cheaper; wide-column writes cost 40% but a lookup by another field scans every partition (3x the scan); time-series writes cost 30% and random point reads 50% more. These are coarse multipliers, not a model of the engines. Storage engine (default B-tree): an LSM engine makes writes about half as costly and reads about 1.5x as costly, and pauses writes for a stall (default 400 ms every 30 s) while it compacts, so its write tail grows while the median stays low (a **compaction** event marks each one). Data size (default off): when `dataGB` exceeds the buffer pool, the missing share of pages is read from disk at 10x the cost. Secondary indexes (default 0): each makes every write 30% slower, and a lookup by another field (the users' `secondaryPct`) costs `readMs x scanMult` (default x20) when there is no index. With the *On-call pairs* workload (two rows, read both, write one) read committed and snapshot isolation let both writers through and the rule across the pair breaks (counted as write skew); serializable locks the pair and the writers take turns. Failover has a detection time and a promotion time; writes newer than the replica's lag are lost (counted), and an unfenced old primary that returns causes split brain. With `topology: multiLeader` (several leaders, each accepting writes for any key and passing them on after `syncLagMs`), two writes to one key at different leaders inside that delay conflict: last-writer-wins drops one (a lost update), a merging counter keeps both. With `backupEverySec` set, *corrupt* and *restore* chaos measure the RPO and RTO. With several leaders, each stamps its writes with its own clock (*Clock offset between leaders* `clockSpreadMs`, *Clock drift* `clockDriftMsPerMin`, *Synchronise clocks every* `clockSyncSec`; the first leader is the reference). *Last writer wins* keeps the later stamp, so a write at a leader that is behind can lose to an older write at one that is ahead even long after the leaders exchanged them; these are counted as *newer writes lost to a clock* and a goal can limit them. *Logical versions* order a write after the one it followed whatever the clocks say, while writes that really were concurrent still conflict. |
| **Read Replica** | 16 | 100 | Same limits as the database. Reads can be **stale** (counted, not failed). Synchronous replication makes every write wait for it (**Sync replica unreachable** if it is down). |
| **Message Queue** | n/a: it only buffers | `capacity` (5,000 jobs) | A full queue refuses new messages (**Queue full (503)**). A message larger than its limit (`maxMessageKB`, 256 KB) is refused as **Message too large**, but only when the users set a request size (`reqKB`; 0 means "not modelled"). It only accepts writes. The backlog grows whenever workers are slower than arrivals. Failing jobs are retried (`maxAttempts`, default 3, growing pauses) and then lost, or parked and counted as dead when the dead-letter queue flag is on; a worker's *poison* share of jobs never succeeds and burns worker time on every attempt. |
| **Topic** | n/a: it only buffers | `capacity` (5,000 messages per subscriber) | Publish/subscribe: every worker it connects to is a subscriber and gets its own copy of every message, with its own backlog, so a slow subscriber falls behind alone and the others and the publisher are unaffected. A subscriber whose backlog is full loses its copies (counted as lost); the publisher is never told. Retries and dead-lettering work as for a queue. Not modelled yet: replay or retention, per-subscriber lag limits. |
| **Log** | n/a: it only buffers | `capacity` (5,000 messages per partition and group) | A partitioned, ordered log. A message goes to one partition (by key, so one key stays in order, or round robin); each worker group (its *consumer group* number) reads every message, and within a group each partition has exactly one reader at a time, worked through one message at a time, so ordering holds per partition and more members than partitions leave the extra ones idle. Failing messages are retried in place (the partition waits). Round robin lets two workers handle one key's messages at once, counted as out-of-order messages. Not modelled yet: rebalance pauses when a member crashes (another member simply takes over), replication and ack modes, retention and replay. |
| **Worker** | `concurrency` (4) | the queue it reads from | It does not fail requests; it falls behind. Watch the backlog and job latency. |
| **CDN** | effectively unlimited | none | It does not fail; misses go to the origin, so a cold start or a short TTL sends a burst there (purging is planned, #11). CDNs can be chained (an edge CDN in front of a shield CDN in front of the origin); a tier with *collapse concurrent misses* sends one request to the origin for a key however many edges miss on it at once. A purge chaos event empties one. With *Range size* (`rangeKB`, a cache has it too) a big object is kept as pieces of that size, each cached and evicted on its own: a request needs every piece, and only the missing ones (their bytes alone) go to the origin, each once when concurrent misses are collapsed; a half-cached hot object therefore costs half the origin bytes (`ranges` tests: 0.502 MB per request against 0.5 by hand). Ranges are not handed on to a second ranged tier. |
| **Rate Limiter** | token bucket: `limitRps` (200) and `burst` (50) | none | Above the rate it rejects on purpose: **Rate limited (429)**. |
| **Shard Router** | n/a: it routes by key | none | It does not fail by itself. A hot key saturates one database while the others idle; a dead shard fails only its keys. |
| **External API** | unlimited (only latency: 80 ms, and an error rate: 1%) | none | Errors are **Vendor errors**. A slow vendor ties up the threads of the servers that wait on it. |
| **Object Store** | `maxConcurrent` (1,000) uploads | none | An app server connected to one uploads the body of each write there first (time to first byte 30 ms plus the body at 50 MB/s per upload, over the link's bandwidth); from then on only a pointer travels, so a queue's message limit no longer applies (the claim-check pattern). With *Multipart chunk* (`multipartKB`, 0 = off) and *Parts in parallel* (`multipartParallel`, 4) a body bigger than a chunk is uploaded in parts: the store's part takes first byte plus ceil(ceil(size/chunk) / parallel) rounds of one chunk's transfer time (10 MB at 50 MB/s: 230 ms single, 90 ms with 1 MB chunks four at a time, 50 ms ten at a time; measured 139.8 and 179.0 ms saved against 140 and 180), while the link in front of the store still carries every byte. Reads never touch it. It stops answering if it crashes (**Node down**, which fails the upload). |
| **Search Shard** | `connections` (16 queries at once) | `queueCap` (50) | One slice of a search index. With the app server's fan-out set to *all*, a read goes to every shard and waits for the last one, so latency is the slowest of N and one dead shard fails every query. *First K* answers once K shards have replied (the others still do the work); *hedging* asks a slow shard again after `hedgeAfterMs` (the same shard, an independent service-time draw, extra load); *partial results* reply with what there is when too few answered, counted as partial. Fan-out is off by default and shards are not used for reads then. |
| **Auth Service** | `connections` (16) | `queueCap` (50) | Says whether a token is valid (`checkMs`, 15 ms). An app server set to *Ask the auth service* (`authMode`) asks it on every request, or once per user while it remembers a yes (`tokenCacheSec`, per user among `tokenUsers`), so the service is on the path of every request: it limits throughput, and when it is down the server either refuses the request (*fail closed*) or lets it through unchecked and counts it (*fail open*, `unchecked`, which a goal can limit). *Verify the signature here* needs no call, only `verifyMs` of CPU, but a revoked token is accepted until it expires. Cryptography is not simulated; these are time and availability costs. The app server's *TLS handshake* (`tlsMs`) is added to the requests that open a new connection (`newConnPct`); a share of them (`tlsResumePct`) resume a saved session at a third of the cost. |
| **Key-Value Store** | `nodes` (5) machines, each working on `concurrency` (8) requests at once | none (a node queues work) | A cluster that keeps `replicas` (N=3) copies of each key. A write goes to all N copies and is acknowledged when `writeQuorum` (W=2) have it; a read asks all N and answers with the newest version among the first `readQuorum` (R=2) to reply, so latency is the kth fastest of N. If R + W is not more than N a read can return an old version (counted as **stale**); with fewer than R or W copies up for a key the request fails as **Not enough copies for a quorum**. The `kvNodeDown` chaos takes nodes out. Optional repair switches: *hinted handoff* (stand-in nodes keep the writes meant for a node that is down and hand them back when it returns), *sloppy quorum* (those stand-ins count towards the write quorum, so writes keep succeeding, but reads of the key do not see them until handed back) and *read repair* (a read writes the newest version back to older copies it found). Not modelled yet: anti-entropy. *How nodes learn a node is down* (`failureDetection`): *instant* (the default), *gossip* (the first node notices after `detectMs`, then every `gossipIntervalMs` each node that knows tells `gossipFanout` others, so the number that know grows by about 1+fanout per round) or *broadcast* (the first node tells every node, `broadcastMs`). A request is received by one live node (a hash of the request); until that node has heard, it sends the request to the dead node as well and waits `probeTimeoutMs` if the quorum cannot be met without it (and a stand-in does not take the write, so no hint is kept for the dead node either). The Inspector shows the time until every node knew and the messages spent. The spread is computed from the order in which nodes hear, not simulated message by message, and a partition that keeps news from one side is not modelled. |
| **Coordinator** | `nodes` (3) in a cluster; one leader handles every request | none | The simulator models a leader-based cluster, as Raft does: writes wait for a majority. Requests go through the leader and cost an operation plus one round trip. Real ZooKeeper may serve reads from a follower, so they can be stale. Losing the leader means no answers for an election: a random time between one and two `electionTimeoutMs` (1,000 ms) plus a round trip. Without a majority of nodes up there is no leader at all and everything fails as **No leader (election or lost quorum)**; a leader that loses its majority steps down. The `clusterNodeDown` and `leaderDown` chaos take nodes out. It also works as a lock and lease service for bookings (the app server setting *Locks come from: coordinator*): a lock is held for its lease and every grant carries a fencing token larger than any before; a database with *Refuse stale lock tokens* turns away a write whose token is older than one it has accepted. A Redis lock issues no token. A database can hand its failover decision to a coordinator it is connected to (*Who decides on failover*): promotion then waits until the coordination service has a leader and a majority. Not modelled yet: sagas and two-phase commit. *Faults to tolerate* (`faultModel`): *crashes* believes the first reply once a majority is alive, so a member that gives a wrong answer is believed (counted as *wrong answers accepted*); *arbitrary* waits for all but `faultsTolerated` (k) replies and needs k+1 matching ones, which takes 3k+1 members and one more round, and a group with fewer refuses most requests. The chaos events `memberOmission` (members drop a share of requests) and `memberLies` (members answer wrongly; mode `corrupt` marks damaged data that *Checksum every answer* drops) inject the faults; a lie carries a valid checksum. The worst case is assumed: liars answer first. Only reads and writes are voted on, not lock grants. Every election starts a higher *term* (shown on the node, on its timeline as "elected for term N", and counted as *Leader elections*). The chaos event `leaderCut` cuts the leader off from the others: they elect a new leader, while the old one goes on acknowledging writes for *Cut-off leader steps down after* (`stepDownSec`, 0 = it stops at once) and those writes are lost (counted as lost writes and as *writes acknowledged by a replaced leader*). Only writes are answered by the old leader, and only while the others still have a majority and no voting model is on. There is no replicated log: a write is a round trip to a majority, and an entry that only some followers hold is not modelled. |
| **Redis** | 1 (single-threaded) | 2,000 | Queue full: **Queue full (503)**. A lock that is held: **Lock busy**. With persistence off, a crash loses what it held. |

### Network card (every component except the users)

The advanced setting *Network card* (`nicMbps`, 0 = unlimited) makes all traffic leaving a machine, its requests to other components and its answers to callers alike, share one first-in-first-out transmitter, the same mechanism as a link's bandwidth. It only has an effect once the users set request or response sizes. With 100 KB answers and 80 Mbit/s the machine sends at most 80e6 / 8 / 100,000 = 100 a second whatever the links beyond it can carry (measured 99.2; 99.0 when 40 KB of requests to the database plus 60 KB of answers share the card). While the card is the bottleneck the server's threads wait on it and its queue fills, so the failure shows as queue-full on that server.

### Backups in an object store

A database wired to an object store restores from it: the backup streams back at the slowest of the link (bandwidth / 8), the store's streams (*Throughput per upload*, times *Parts in parallel* when *Multipart chunk* is on, else one stream) and the database's own *Restore speed*, after the store's time to first byte, and the database answers nothing for that long (the recovery time, RTO). A 20 GB database over one 50 MB/s stream takes 409.6 s whatever the link; four parts at once need a link of at least 1,600 Mbit/s to reach 200 MB/s and take 102.4 s (measured equal to the hand figures). Without a store behind the database, *Restore speed* alone sets the time, as before. The download is not billed as egress.

### Failure reasons you will see

Timeouts, Queue full (503), Node down, Stale DNS record, No route, No healthy backend, Rate limited (429), Call timeouts (504), Circuit open, Vendor errors, Lock busy, Waited too long in queue, DB connections refused, No primary: failing over, Sync replica unreachable, Message too large, Connection lost (six packets in a row lost on a lossy link), Transaction aborted, Poison job, Not enough copies for a quorum, No leader (election or lost quorum). The chart shows them in "Why requests failed", and the Request traces tab explains one request at a time.

### DNS record caching

The Users component's advanced `dnsTtlSec` setting caches a connected target's address. While the selected target is down and its cached record is within the TTL, attempts fail as **Stale DNS record**; after expiry the client stops choosing it and resolves again. The default 0 keeps existing routing behaviour and does not model DNS lookups. With caching enabled, the initial resolution and each expiry count as a lookup. Each lookup costs $0.00001 and is included in the hourly cost rate, so shorter TTLs can restore traffic sooner at the cost of more lookups.

## Chaos you can inject

Crash (with automatic restart), slow-down (steady or pulsing), network partition (a node that never answers, not one that refuses), and for databases a failover with detection and promotion times. A crash fails the requests already in flight on that node. Every component except the users can be placed in an availability zone (advanced setting, default Zone A); a call between two zones pays 1.5 ms each way, and a *zone outage* crashes everything placed in a zone together, so a design with every server in one zone loses everything while one spread over two keeps serving (a load balancer in the failed zone is lost with it). Every component, users included, sits in a region (US, Europe or Asia-Pacific, default US): a call between regions pays the distance each way (US-Europe 45 ms, US-Asia 75 ms, Europe-Asia 100 ms) and a *region outage* (`regionDown`) crashes everything placed in a region at once. Also a one-way or two-way connection failure (`linkDown`) and a purge that empties a cache or CDN. For databases with `backupEverySec` set: *corrupt* (silent damage from that moment) and *restore* (back to the last backup taken before the damage, losing every write since: the RPO; the database is unavailable while the backup streams back at `restoreMBps`: the RTO). Also *kvNodeDown* for a key-value store cluster.

## Why these rules are believable

- **Queueing theory.** A single-server queue is tested against the Pollaczek-Khinchine formula and a multi-server queue against the Allen-Cunneen approximation (`queueing_test.go`, `variability_test.go`). The mean wait the engine produces matches those results within a stated tolerance across several loads.
- **Determinism.** Same diagram and seed, same result, so a failure you see can be reproduced, rewound (the rewind slider replays exactly) and compared.
- **Each behaviour is a checked scenario.** A retry storm that outlives its trigger, a cache stampede, a stuck-thread outage behind a silent database, split brain after failover, an autoscaler that boots too slowly: each is a challenge whose starting design must fail and whose fix must pass, with identical stars on seeds 1-8 (`scenarios_test.go`). Several first drafts were not winnable and were retuned.
- **Capacity numbers are measured, not guessed.** For example, three 16-thread app servers behind a cache and a database carried about 1,157 requests a second (the "roughly 400 per server" used by the interview calculator).
- **The design lint reproduces the same patterns** statically (`lint.go`), and its rules are cross-checked against the challenge designs.

## What the defaults are, and are not

The defaults (8 threads, 16 database slots, a 50-request queue, and so on) are round, plausible numbers chosen so that interesting failures appear at loads that run comfortably in a browser. They are not benchmarks of any real server or database, and you should not read "a server handles 400 requests a second" as a fact about the world. The *shape* (utilisation rises, queues build, timeouts follow, retries amplify) is the point.

## Out of scope on purpose

- Omission and wrong-answer faults exist only for a coordinator group (see its row); other components do not drop or corrupt messages.
- Vector clocks and sibling values are not simulated: logical versions order writes that follow each other, and concurrent writes still lose one. A cache's clock offset (`clockSkewMs`) and the leaders' clocks in a multi-leader database are the only clocks modelled; lease expiry does not use them.
- General DNS records and service discovery are not simulated; Users has a small DNS-cache model for connected targets. Peer-to-peer systems and blockchains are not simulated.
- Cryptography itself, authorisation rules, delegation and firewalls are not simulated; authentication and encryption exist only as time and availability costs (Auth Service, signature checks, TLS handshakes).
- Consensus is a leader, a term and a majority: there is no replicated log, no proposals and no real Paxos or Raft messages, and no blockchain consensus.
- Containers are modelled by their boot time and cost, and serverless functions by a cold start; images, density per host, orchestration and peer-to-peer or blockchain systems are not simulated.
- Reliable and atomic multicast, ordering across receivers and multicast trees are not simulated; gossip exists only to spread the news of a failed key-value node. Arbitrary faults are modelled for a coordinator group's reads and writes only (no signatures, no lock grants, no faulty leader).
- A stream job can recover from a crash with a message log (`recovery`, `logMs` per event, `replayMs` per replayed event): it replays the events since its last checkpoint and sends no output twice, where a checkpoint alone handles them again at full cost and repeats outputs unless delivery is exactly-once. The run reports the catch-up time and the repeated outputs; goals can limit both.

## What is not modelled yet

downloads from the object store, and storage or egress cost (replicas per search shard; a link can have a bandwidth limit, a queue a message limit and a cache or CDN a byte capacity, once the users set request or response sizes); clock skew and fsync loss of unflushed writes (disk IOPS as a queue for writes exists; GC pauses, packet loss, jitter, CPU burst credits and out-of-memory kills exist); (write skew and isolation levels, data volume, storage engines and coarse data-model presets exist; secondary indexes and isolation levels exist); regions, zones and deployments; consensus and distributed data; stream windows and approximate data structures; LLM serving. These are tracked as GitHub issues #11, #13, #16, #17, #18, #19, #20 and #21.
